### Introduction

DapperGlib is an extension built on top of [Dapper](https://github.com/DapperLib/Dapper "Dapper repository"), designed to provide a more expressive and convenient way to work with database queries using APIs inspired by [Laravel Eloquent](https://laravel.com/framework/docs/eloquent "eloquent").
It includes Relationships, Query Builder, Basic Where Clauses, Advanced Where Clauses, Ordering, generic column retrieval and more.

> **DapperGlib is not a replacement for Dapper, nor does it compete with it.**  
> It is an extension built on top of Dapper that adds conventions and higher-level APIs inspired by Laravel Eloquent, while keeping Dapper as the underlying data-access engine. DapperGlib simply provides an additional layer for common tasks such as model-based queries, relationships, asynchronous operations, stored procedures, multiple result sets and raw SQL execution. You can use DapperGlib where its abstractions are useful and continue using Dapper directly whenever you need full control.

Starting with version **1.4.0**, query values generated by the Query Builder are executed using Dapper parameters instead of being directly concatenated into the SQL statement. This improves type handling and makes common queries safer and easier to debug.

Version **1.5.0** builds on the 1.4.5 async and DB API foundation and adds batched model inserts with `CreateMany` / `InsertMany`, high-throughput SQL Server bulk copy with `BulkInsert`, partial/dynamic `Create` and `Update`, shared execution contexts, automatic and manual transactions, stronger connection isolation and additional validation around generated SQL and model columns.

Version **1.6.0** introduces metadata-based model relationships with `[HasMany]`, `[HasOne]` and `[BelongsTo]`, eager loading through `With()`, nested relationships, constrained eager loading, relationship load tracking, `Load` / `LoadMissing`, `Chaperone`, metadata-based `WhereHas`, relationship projections such as `WithCount`, `WithExists`, `WithSum`, `WithAvg`, `WithMin` and `WithMax`, and strongly typed lambda overloads for the Where API. The eager-loading engine uses grouped secondary queries instead of automatic JOINs so parent rows are not multiplied by `HasMany` cardinality.

DapperGlib 1.6.0 provides targets for:

- .NET 6.0
- .NET 8.0
- .NET 10.0

## Getting Started

### #Model Conventions
As I mentioned before DapperGlib is inspired by Eloquent Laravel, so we will be working with Models. let's examine a basic model class and explain each part.

```C#
using DapperGlib;

namespace App.Models
{
    public class User : Model<User>
    {
        public User()
        {
        }
    }
}
```

The connection string by default is called **SqlConnection** if you use multiple connections or rename default connection string name you must specify it on Models


```C#
using DapperGlib;

namespace App.Models
{
    public class User : Model<User>
    {
        public override string Connection { get; set; } = "AnotherSqlConnection";
    
        public User()
        {
        }
    }
}
```


#### #Table Names
After looking at the example above, you may have noticed that we didn't specify which database table corresponds to our **User** Model. This is because the name of the Class will be used as the name of the table **unless** another name is explicitly specified. So in this case it will be assumed that the **User** model stores records in the User table

If your model's corresponding database table does not fit this convention, you may manually specify the model's table name by defining a table property on the model:

```C#
public class User : Model<User>
{
    [TableName]
    public override string? Table => "Users";
    ...
}
```
> **Note that the TableName attribute must be used on the Property**

#### #Table Schemas
If the table is within a schema it must be specified by overriding the Schema property and using the Schema attribute.

```C#
public class User : Model<User>
{
    [Schema]
    public override string? Schema => "UserSchema";
    ...
}
```

#### #Primary Keys
Unlike the table name, the primary key property must always be specified. The primary key will be used for action queries like Update, Find, Delete, Etc.
We need to use the **PrimaryKey** Attribute on the Property.

```C#
public class User : Model<User>
{
    [PrimaryKey]
    public int UserId { get; set; }
    ...
}
```

By default DapperGlib assumes that the primary key is generated by the database. Starting with version **1.4.5**, primary keys are no longer limited to `int`: methods such as `Find`, `FindAsync`, `FindOrDefault` and `FindOrDefaultAsync` support generic key types such as `long`, `Guid`, `string` and other compatible CLR types.

Generated primary keys are retrieved using SQL Server `OUTPUT INSERTED`, avoiding `@@IDENTITY` and allowing the generated value to be assigned back to the model using its native CLR type.

If you use a non-incrementing primary key, define the `Incrementing` property on your model as `false`:

```C#
public class User : Model<User>
{
    public override bool Incrementing => false;
    ...
}
```


#### #Fillable Properties
Properties that are to be filled and are defined in the Model table must be specified with the **Fillable** attribute.

```C#
public class User : Model<User>
{
    [Fillable]
    public string Name { get; set; }
    ...
}
```

### #Inserting & Updating Models
Once you have created a model and its associated database table, you are ready to start interacting with data from your database. You can think of each **Model** as a query builder allowing you to fluently query the database table associated with the model.

#### #Insert
Now insert records will be very simple.  
To insert a new record into the database, you should instantiate a new Model instance and set attributes on the Model. Then, call the **Insert** method on the Model instance:

```C#
User UserToSave = new();

UserToSave.Name = "Keanu";
UserToSave.LastName = "Reeves";

UserToSave.Insert();
```

You can keep it simpler by using:

```C#
User NewUser = User.Create(new()
{
    Name = "Keanu",
    LastName = "Reeves"
});
```


Starting with version **1.5.0**, `Create` also accepts a partial anonymous object. Only the properties you provide are included in the generated `INSERT`:

```C#
User NewUser = User.Create(new
{
    Name = "Keanu",
    LastName = "Reeves"
});
```

The provided property names must exist on the model and must be marked with `[Fillable]` (except for a valid non-incrementing primary key). Values are always sent as Dapper parameters. Properties that are not provided are omitted from the `INSERT`, so database defaults can apply to omitted columns.

The asynchronous equivalent supports `CancellationToken`:

```C#
User NewUser = await User.CreateAsync(
    new
    {
        Name = "Keanu",
        LastName = "Reeves"
    },
    cancellationToken
);
```

#### #CreateMany / InsertMany / BulkInsert

Version **1.5.0** adds three APIs for inserting multiple models. They are intentionally different because they optimize for different use cases.

| API | Strategy | Generated identities | Best use case |
| --- | --- | --- | --- |
| `CreateMany` | Parameterized multi-row SQL in chunks | **Returned and assigned back to each model** when the primary key is generated by the database | You need the inserted models with their generated primary keys |
| `InsertMany` | Parameterized `INSERT ... VALUES` in chunks | **Not hydrated** into the CLR models | You need efficient batched inserts and do not need generated identities in memory |
| `BulkInsert` | SQL Server `SqlBulkCopy` streaming | **Not hydrated** into the CLR models | Highest-throughput inserts for large SQL Server workloads |

`CreateMany` example:

```C#
var users = new[]
{
    new User { Name = "Keanu", LastName = "Reeves" },
    new User { Name = "Tom", LastName = "Hanks" }
};

List<User> createdUsers = User.CreateMany(users);

// When UserId is an incrementing PK, each model now has its generated UserId.
```

`CreateMany` has additional cost because DapperGlib correlates the generated database keys back to the original model instances.

`InsertMany` example:

```C#
var users = new[]
{
    new User { Name = "Keanu", LastName = "Reeves" },
    new User { Name = "Tom", LastName = "Hanks" }
};

User.InsertMany(users);

// Rows are inserted, but generated identity values are not assigned back to users.
```

`BulkInsert` example:

```C#
var users = new[]
{
    new User { Name = "Keanu", LastName = "Reeves" },
    new User { Name = "Tom", LastName = "Hanks" }
};

User.BulkInsert(users);
```

> **`BulkInsert` is SQL Server-specific.** It uses `Microsoft.Data.SqlClient.SqlBulkCopy` and is intended for high-volume SQL Server inserts. It does not generate one parameter per row and does not hydrate generated identities.

Async overloads are available for all three paths that need asynchronous execution:

```C#
List<User> created = await User.CreateManyAsync(users, cancellationToken);

await User.InsertManyAsync(users, cancellationToken);

await User.BulkInsertAsync(users, cancellationToken);
```

`CreateMany` and `InsertMany` automatically split large collections into chunks so a generated SQL command never exceeds DapperGlib's SQL Server parameter budget. The current budget is **2000 parameters per command**, with a hard cap of **1000 rows per chunk**.

> **Atomicity note:** without an explicit transaction, successfully completed chunks remain committed if a later chunk fails or is cancelled. Wrap the operation in a DapperGlib transaction when all rows must succeed or fail together.

For mapped nullable columns, an explicit `null` is sent as SQL `NULL`. Database defaults apply when a column is omitted from the generated insert, not when an explicit `NULL` is sent.

#### #Update
You can use the **Update** function to update an existing Model in the database.  
The Update function will create a query based on **ALL Fillable Properties** and the **Primary Key** and update the record in the database.  
Following the example above:

```C#

NewUser.Name = "Tom";
NewUser.LastName = "Hanks";
NewUser.Update(); 

```
If you want to update only specific properties you can pass an anonymous object to the Update method
```C#
NewUser.Update(new
{
    LastName = "Holland",
});

```


Starting with version **1.5.0**, partial updates validate the provided property names before any SQL is executed. Every updated property must exist on the model and be marked with `[Fillable]`; the primary key cannot be included in the partial update object. Only the provided columns are included in the `SET` clause, while the primary key is used only in the `WHERE` clause.

```C#
await NewUser.UpdateAsync(
    new
    {
        LastName = "Holland"
    },
    cancellationToken
);
```

Partial update values are sent through Dapper parameters and are not concatenated into the generated SQL.

### #Retrieving Models

#### #Retrieving All Rows From A Table
Of course you can get data from your database using very simple functions.  
The model's **ToList** method will retrieve all of the records from the model's associated database table:

```C#
List<User> Users = User.ToList();
```

#### #Retrieving A Single Row / Column From A Table
If you just need to retrieve a single row from a database table, you may use the **First** method:

```C#
User user = User.First();
```

If you only need one column from the first matching record, you may use **Value**.

The original string overload is still available:

```C#
string name = User.Where("UserId", 10).Value("Name");
```

You can also use the generic **Value<T>()** overload to retrieve strongly typed values:

```C#
int votes = User.Where("UserId", 10).Value<int>("Votes");

decimal balance = User.Where("UserId", 10).Value<decimal>("Balance");

Guid code = User.Where("UserId", 10).Value<Guid>("Code");
```

If you need one column from multiple records, use **Pluck<T>()**:

```C#
List<int> userIds = User.Where("Active", true).Pluck<int>("UserId");

List<string> emails = User.Where("Active", true).Pluck<string>("Email");
```

`Value<T>()` and `Pluck<T>()` can also be used after relationship queries because relationships inherit from the Query Builder.

```C#
List<int> commentIds = user.Comments
    .Where("Likes", ">", 10)
    .Pluck<int>("CommentId");
```


#### #Find a record in Table
If you just need to find a single row from a database table using **Primary Key**, you may use **Find** method:

```C#
User user = User.Find(10);
```

`Find` and `FindAsync` throw a **ModelNotFoundException** when the requested primary key does not exist.  
If you prefer to receive `null`, use **FindOrDefault** or **FindOrDefaultAsync**.

You can delete a record using the **Delete** function:

```C#
NewUser.Delete();
```

```C#
await NewUser.DeleteAsync();
```

## Query Builder
Query Builder provides a convenient fluent interface for creating and executing database queries. It can be used to perform most database operations.

Values supplied through normal Query Builder methods are executed using **Dapper parameters**. For example:

```C#
var users = User
    .Where("Name", "Tom")
    .Where("Votes", ">", 10)
    .ToList();
```

is executed using parameter bindings instead of inserting `"Tom"` and `10` directly into the SQL string.

You can inspect the generated bindings using **GetBindings()**, described in the Util section.

### #Basic Where Clauses

#### #Where Clauses
You may use the query builder's where method to add "where" clauses to the query. The most basic call to the where method requires three arguments. The first argument is the name of the column. The second argument is an operator, which can be any of the database's supported operators. The third argument is the value to compare against the column's value.

```C#
var user = User.Where("Name", "=", "Tom").First();
```
If you want to verify that a column is `=` to a given value, you may pass the value as the second argument to the where method.  
The Query Builder will assume you would like to use the `=` operator:

```C#
var user = User.Where("Name", "Tom").First();
```

As previously mentioned, you may use any operator that is supported by your database system:

```C#
var user = User.Where("Name", "like", "%Tom%").First();

var users = User.Where("Votes", ">=", 10).ToList();
```

#### #Strongly Typed Where Clauses

Version **1.6.0** adds strongly typed lambda overloads for the Where API. The original string overloads remain available, so existing code continues to work.

Instead of:

```C#
var users = User
    .Where("Active", true)
    .Where("Votes", ">=", 10)
    .ToList();
```

you can write:

```C#
var users = User
    .Where(x => x.Active, true)
    .Where(x => x.Votes, ">=", 10)
    .ToList();
```

The lambda must point directly to a public property on the model. Nested or computed expressions such as `x => x.Profile.Name` or `x => x.Votes + 1` are not treated as columns.

Strongly typed overloads are available on `Model<T>`, `QueryBuilder<T>`, `SubQuery<T>` and `EagerLoadBuilder<T>` for the Where family, including common methods such as:

```C#
User.Where(x => x.UserId, 10);
User.WhereIn(x => x.UserId, new[] { 1, 2, 3 });
User.WhereNotIn(x => x.UserId, excludedIds);
User.WhereNull(x => x.LastName);
User.WhereNotNull(x => x.Email);
User.WhereLike(x => x.Name, "%Tom%");
User.WhereContains(x => x.Name, "Tom");
User.WhereDate(x => x.Birthday, "2022-07-01");
User.WhereYear(x => x.Birthday, "2022");
User.WhereMonth(x => x.Birthday, "07");
User.WhereDay(x => x.Birthday, "01");
User.WhereColumn(x => x.Name, x => x.LastName);
User.WhereBetween(x => x.Votes, new() { From = 5, To = 10 });
```

They also work inside grouped conditions and relationship constraints:

```C#
var users = User.Where(q => q
    .Where(x => x.Active, true)
    .OrWhere(x => x.Votes, ">", 100)
).ToList();
```

#### #Or Where Clauses
When chaining together calls to the query builder's where method, the "where" clauses will be joined together using the and operator.  
However, you may use the orWhere method to join a clause to the query using the or operator. The orWhere method accepts the same arguments as the where method:

```C#
var users = User.Where("Name","Tom").OrWhere("Name", "Keanu").ToList();
```

#### #WhereLike / WhereContains

Use **WhereLike** when you want to provide the SQL LIKE pattern yourself:

```C#
var users = User.WhereLike("Name", "%Tom%").ToList();

var gmailUsers = User.WhereLike("Email", "%@gmail.com").ToList();
```

Use **WhereContains** when you simply want to search for a value contained anywhere in a string:

```C#
var users = User.WhereContains("Name", "Tom").ToList();
```

`WhereContains` automatically builds the `%value%` pattern and treats LIKE wildcard characters in the provided value as literal characters.

Both methods use Dapper parameters internally.

#### #Additional Where Clauses

> WhereBetween / WhereNotBetween / WhereDateBetween

The **WhereBetween** method verifies that a column's value is between two values.  
Receives two parameters, the first is the column's name and the second is an instance of the **DapperGlib.Util.Between** class which only has **From** and **To** properties

```C#
var users = User.WhereBetween("Votes", new() { From = 5, To = 10 }).ToList();
```

The **WhereNotBetween** method verifies that a column's value lies outside of two values:

```C#
var users = User.WhereNotBetween("Votes", new() { From = 5, To = 10 }).ToList();
```

The **WhereDateBetween** method verifies that a column's value is between two Dates.  
Receives two parameters, the first is the column's name and the second is an instance of the **DapperGlib.Util.DateBetween** class which only has **From** and **To** properties

```C#
var users = User.WhereDateBetween("Birthday", new() { From = "1956-07-09", To = "1996-06-01" }).ToList();
```

> WhereNot / OrWhereNot  

The **WhereNot** and **OrWhereNot** methods may be used to negate a given group of query constraints

```C#
var users = User.WhereNot((Builder) =>
{
    return Builder.Where("Votes", ">", 10);
}).ToList();
```

> WhereIn / WhereNotIn

The **WhereIn** method verifies that a given column's value is contained within a collection.

Starting with version 1.4.0 you can use typed arrays and generic collections directly:

```C#
var users = User.WhereIn("UserId", new int[] { 2, 3, 4 }).ToList();
```

```C#
var ids = new List<int> { 2, 3, 4 };

var users = User.WhereIn("UserId", ids).ToList();
```

Strings are also supported:

```C#
var emails = new List<string>
{
    "john@example.com",
    "jane@example.com"
};

var users = User.WhereIn("Email", emails).ToList();
```

The existing `object[]` overload remains available for backward compatibility:

```C#
var users = User.WhereIn("UserId", new object[] { 2, 3, 4 }).ToList();
```

The **WhereNotIn** method works in the same way, but verifies that the column's value is not contained within the collection:

```C#
var excludedIds = new List<int> { 2, 3, 4 };

var users = User.WhereNotIn("UserId", excludedIds).ToList();
```

Collections passed to `WhereIn` and `WhereNotIn` are sent through Dapper collection parameters instead of being manually concatenated into the SQL statement.

The collection cannot be empty and, starting with the stabilized 1.4.5 implementation, null members are rejected. Use `WhereNull()` explicitly when querying SQL `NULL` values.

> WhereNull / WhereNotNull

The **WhereNull** method verifies that the value of the given column is NULL:
```C#
var users = User.WhereNull("LastName").ToList();
```

The **WhereNotNull** method verifies that the value of the given column is NOT NULL:

```C#
var users = User.WhereNotNull("LastName").ToList();
```
> WhereDate / WhereYear / WhereMonth / WhereDay

The **WhereDate** method may be used to compare a column's value against a date:

```C#
var users = User.WhereDate("Birthday", "2022-07-01").ToList();
```

The **WhereYear** method may be used to compare a column's value against a specific year:

```C#
var users = User.WhereYear("Birthday", "2022").ToList();
```

The **WhereMonth** method may be used to compare a column's value against a specific month:

```C#
var users = User.WhereMonth("Birthday", "07").ToList();
```

The **WhereDay** method may be used to compare a column's value against a specific day of the month:

```C#
var users = User.WhereDay("Birthday", "01").ToList();
```
> WhereDateDiff

The **WhereDateDiff** method is used to compare the difference between a column of type date and a given date.

###### Parameters
- Column
- Date
- ComparisonOperator (opcional)
  * All comparison operators supported by sql server, default is **=**
- Difference
  * This is the difference to be expected in the comparison
- ComparisonType
  * It can be Year, Month, Day, Minute
- Invert (opcional)
  * Reverse the order of the first and second parameters this to control if the greatest date goes first or last


```C#
using DapperGlib.Util;

var users = User.WhereDateDiff("RegistrationDate", DateTime.Now.ToString(), 3, DateDiff.YEAR).ToList(); //Users who registered 3 years ago
```
Optionally you can also pass the comparison operator.

```C#
var users = User.WhereDateDiff("RegistrationDate", DateTime.Now.ToString(), ">=", 3, DateDiff.YEAR).ToList(); 
```

> WhereColumn

The **WhereColumn** method may be used to verify that two columns are equal:

```C#
var users = User.WhereColumn("Name", "LastName").ToList();
```

You may also pass a comparison operator to the whereColumn method:

```C#
var users = User.WhereColumn("Name", "!=", "LastName").ToList();
```

> **Note: The columns must be of the same type**

> WhereRaw

The **WhereRaw** method is used to pass your own query for the conditional.

```C#
var users = User.Query().WhereRaw("name = 'Math' and city = 'London' ").ToList();
```

> **Security note:** `WhereRaw` is raw SQL and is not automatically rewritten into Dapper parameters. Do not concatenate untrusted user input into raw clauses.

#### #Logical Grouping

Sometimes you may need to group several "where" clauses within parentheses in order to achieve your query's desired logical grouping. In fact, you should generally always group calls to the orWhere method in parentheses in order to avoid unexpected query behavior. To accomplish this, you may pass a closure to the where method:

```C#
var users = User.Where("Votes", ">", 100).Where((Builder) =>
{
    return Builder.Where("Votes", ">", 10).OrWhere("Name", "Robert Downey Jr.");
}).ToList();
```
> SQL Output: **select * from Users where Votes > 100 and (Votes > 10 or Name = 'Robert Downey Jr.')**

you can do the same with the OrWhere method

```C#
var users = User.Where("Votes", ">", 100).OrWhere((Builder) =>
{
    return Builder.Where("Votes", ">", 10).Where("Name", "Abigail");
}).ToList();
```

> SQL Output: **select * from Users where Votes > 100 or (Votes > 10 and Name = 'Abigail')**

### #Mass Updates
Updates can also be performed against models that match a given query using the update method with passing an anonymous object.  
In this example, all users that have a destination of San Diego will be updated:

```C#
User.Where("Destination", "San Diego").Update(new {
    Delayed = 1
});
```

### #Mass Delete
The query builder's delete method may be used to delete records from the table. You may constrain delete statements by adding "where" clauses before calling the delete method:

```C#

User.Query().Delete(); // Delete All records

User.Where("Name", "Tom").Delete(); // Delete records with Name 'Tom'

```
If you wish to truncate an entire table, which will remove all records from the table and reset the auto-incrementing ID to zero, you may use the Truncate method:

```C#

User.Truncate();

```
### #Select Statements & Grouping

#### #Specifying A Select Clause
You may not always want to select all columns from a database table. Using the `Select` method, you can specify a custom "select" clause for the query:

```C#
var users = User.Select("Name", "Email").ToList();
```

You can create a class to save only the fields you want to select 
Retrieving methods can receive a generic to map the response to a different class than the model

```C#
public class SelectUser
{
    public string Name { get; set; }
    public string UserEmail { get; set; }
}
var users = User.Select("Name", "Email as UserEmail").ToList<SelectUser>();
```
#### #Grouping

##### GroupBy

As you might expect, the `GroupBy` method may be used to group the query results.

```C#
public class CategoriesWithMoreProducts
{
    public int CategoryId { get; set; }
    public int Products { get; set; }
}
var categories = Product.Select("CategoryId","count(*) as Products").GroupBy("CategoryId").ToList<CategoriesWithMoreProducts>();
```
> The GroupBy method should always be used with the Select method!

##### Having
The `Having` method's signature is similar to that of the where method:

```C#
var categories = Product.Select("CategoryId","count(*) as Products").GroupBy("CategoryId").Having("CategoryId","=", 5).ToList<CategoriesWithMoreProducts>();
```

To build more advanced having statements, use the `HavingRaw` method.
```C#
var orders = Order.Select("Department","SUM(Price) as TotalSales").GroupBy("Department").HavingRaw("SUM(price) > 200").ToList();
```

### #Ordering, Limit & Offset

#### #Ordering

The **OrderBy** method allows you to sort the results of the query by a given column. The first argument accepted by the orderBy method should be the column you wish to sort by, while the second argument determines the direction of the sort and may be either asc or desc:

```C#
var users = User.OrderBy("Name").ToList();

var users = User.OrderBy("Name", "DESC").ToList();
```

To sort by multiple columns, you may simply invoke orderBy as many times as necessary:

```C#
var users = User.OrderBy("Name").OrderBy("LastName").ToList();
```

you can also randomize them using method **InRandomOrder**

```C#
var users = User.InRandomOrder().ToList();
```

#### #Limit & Offset
You may use the **Skip** and **Take** methods to limit the number of results returned from the query or to skip a given number of results in the query:

```C#
var users = User.Take(10).ToList(); // returns the top 10 users
var users = User.Skip(10).ToList(); // returns all users skipping the previous 10
var users = User.Skip(10).Take(10).ToList(); // returns the next 10 users skipping the previous 10
```
> The Order and Limit methods should always be at the end of the query. you can't add any kind of conditional after them

### #Per Query Timeout

Version **1.4.5** adds a fluent timeout in seconds:

```C#
var users = await User
    .Where("Active", true)
    .Timeout(5)
    .ToListAsync();
```

It can also be used directly from a model:

```C#
var users = await User
    .Timeout(10)
    .ToListAsync();
```

and from relationships:

```C#
var comments = await user.Comments
    .Timeout(5)
    .ToListAsync();
```

A per-query timeout overrides the global `DapperGlib:CommandTimeout` setting.

### #CancellationToken

Async APIs expose `CancellationToken` overloads so cancellation can be propagated to Dapper / `Microsoft.Data.SqlClient` operations.

```C#
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(10));

List<User> users = await User
    .Where("Active", true)
    .ToListAsync(cts.Token);
```

Version **1.5.0** also supports cancellation on the new batched APIs and transaction APIs:

```C#
await User.CreateManyAsync(users, cancellationToken);
await User.InsertManyAsync(users, cancellationToken);
await User.BulkInsertAsync(users, cancellationToken);

await DB.Connection().TransactionAsync(
    async () =>
    {
        await User.InsertManyAsync(users, cancellationToken);
    },
    System.Data.IsolationLevel.ReadCommitted,
    cancellationToken
);
```

A token that is already cancelled is rejected before the next cancellable operation starts. During chunked operations, cancellation is checked between chunks and is also passed to the underlying async database command. A cancellation that occurs while SQL Server is executing may be surfaced by the provider as a cancellation-related `SqlException` instead of only as `OperationCanceledException`.

> If a chunked operation is not inside a transaction, rows from earlier completed chunks may remain persisted after cancellation. Inside `TransactionAsync`, cancellation or another exception causes the transaction to roll back.

### #Conditional Clauses

Sometimes you may want certain query clauses to apply to a query based on another condition.  
For instance, you may accomplish this using the **When** method:

```C#
var users = User.When(4 == 4, (Builder) =>
{
    return Builder.WhereNotNull("LastName");
}).ToList();
```

### #Aggregates
The query builder also provides a variety of methods for retrieving aggregate values like **Count**, **Max**, **Min**, **Avg** and **Sum**. You may call any of these methods after constructing your query:

```C#
double price  = Product.Max("Price");
```
Of course, you may combine these methods with other clauses to fine-tune how your aggregate value is calculated:

```C#
int TotalProductsWithDiscount  = Product.Where("Discount", ">", 0).Count();
double MaxPriceDiscount = Product.Where("Discount", ">", 0).Max("Price");
double TotalPriceDiscount = Product.Where("Discount", ">", 0).Sum("Price");
```
#### #Determining If Records Exist

Instead of using the count method to determine if any records exist that match your query's constraints, you may use the Exists and DoesntExist methods:

```C#

if(Product.Where("Discount", ">", 0).Exists()){
  // ...
}

if(Product.Where("Discount", ">", 0).DoesntExist()){
  // ...
}

```

### #Distinct
The **Distinct** method allows you to force the query to return distinct results:

```C#
var products = Product.Distinct().ToList();
```
> SQL Output: **select DISTINCT * from Product**

You can specify the fields by passing a string separated by commas

```C#
var products = Product.Distinct("Name, Price").ToList();
```
> SQL Output: **select DISTINCT Name, Price from Product**

You can get an instance of the QueryBuilder without conditions with the `Query` method:
```C#
var Builder = Product.Query();
```
You can clone an instance of the QueryBuilder using the `Clone` method:

```C#
var Builder1 = Product.Where("CategoryId", 5);
var Builder2 = Builder1.Clone();
```
You can get the name of the table related to the Model with the `GetTableName` method:

```C#
string table = Product.GetTableName();
```
You can get the debug SQL output from the QueryBuilder using the `ToSql` method:

```C#
string sql = Product.Where("CategoryId", 5).ToSql();
```

You can inspect the parameterized SQL separately:

```C#
string sql = Product
    .Where("CategoryId", 5)
    .ToParameterizedSql();
```

and inspect the generated bindings with:

```C#
var bindings = Product

```

## Relationships

### #Introduction

Version **1.6.0** introduces a metadata-based relationship system designed for model navigation properties, eager loading and relationship-aware query operations.

Relationships are defined directly on model properties with:

- `[HasMany]`
- `[HasOne]`
- `[BelongsTo]`

The relationship metadata is cached and reused by `With`, `WhereHas`, `WhereDoesntHave`, `Relation`, `Load`, `LoadMissing`, `WithCount`, `WithExists` and relationship aggregates.

> DapperGlib does **not** enable lazy loading automatically. A navigation property is populated when you eager-load it with `With()`, explicitly load it with `Load()`, or assign it yourself.

### #Defining Relationships

Consider these models:

```C#
public class User : Model<User>
{
    [PrimaryKey]
    public int UserId { get; set; }

    [HasMany(nameof(UserId), Chaperone = true)]
    public List<Post> Posts { get; set; } = new();

    [HasOne(nameof(UserId))]
    public UserProfile? Profile { get; set; }
}

public class Post : Model<Post>
{
    [PrimaryKey]
    public int PostId { get; set; }

    [Fillable]
    public int UserId { get; set; }

    [BelongsTo(nameof(UserId))]
    public User? User { get; set; }
}

public class UserProfile : Model<UserProfile>
{
    [PrimaryKey]
    public int UserProfileId { get; set; }

    [Fillable]
    public int UserId { get; set; }
}
```

When the local and related key have the **same property name**, the related key may be omitted. For example:

```C#
[HasMany(nameof(UserId))]
public List<Post> Posts { get; set; } = new();
```

represents:

```text
User.UserId -> Post.UserId
```

If the property names are different, pass both keys explicitly:

```C#
[HasMany(nameof(UserId), nameof(Post.AuthorId))]
public List<Post> Posts { get; set; } = new();
```

The same shorthand applies to `HasOne` and `BelongsTo` when both sides use the same key name.

### #HasMany

`HasMany` represents a collection relationship:

```C#
[HasMany(nameof(UserId))]
public List<Post> Posts { get; set; } = new();
```

DapperGlib expects a writable collection navigation property and validates the relationship metadata before executing relationship-aware operations.

### #HasOne

`HasOne` represents a single related model:

```C#
[HasOne(nameof(UserId))]
public UserProfile? Profile { get; set; }
```

The navigation property may be `null` when no related row exists.

### #BelongsTo

`BelongsTo` represents the inverse side where the current model stores the key that points to another model:

```C#
[BelongsTo(nameof(UserId))]
public User? User { get; set; }
```

If the names differ:

```C#
[BelongsTo(nameof(AuthorId), nameof(User.UserId))]
public User? Author { get; set; }
```

### #Eager Loading With

Use `With()` to preload relationships and avoid N+1 query patterns:

```C#
List<User> users = User
    .With(x => x.Posts)
    .ToList();
```

String overloads are also available:

```C#
List<User> users = User
    .With(nameof(User.Posts))
    .ToList();
```

You can eager-load multiple relationships:

```C#
List<User> users = User
    .With(x => x.Posts)
    .With(x => x.Profile)
    .ToList();
```

`With()` works with model-returning terminal methods such as `ToList`, `First`, `FirstOrDefault`, `Single`, `SingleOrDefault`, `Find` and their asynchronous equivalents.

> Projection terminal methods that materialize a different result type cannot be combined with `With()`, because eager loading requires actual model instances.

### #How Eager Loading Executes

DapperGlib 1.6.0 uses grouped secondary queries instead of automatically joining relationship tables.

For a `HasMany` relationship the general strategy is:

```text
1 query -> parent models
1 or more grouped queries -> related models using WHERE relatedKey IN (...)
```

This avoids repeating the parent row for every child as a JOIN would do. The eager loader also respects SQL Server's parameter limit by chunking parent keys when necessary.

For `HasMany`, `Skip()` and `Take()` inside an eager-load constraint are applied **per parent** using a partitioned `ROW_NUMBER()` query.

### #Constrained Eager Loading

Use an `EagerLoadBuilder<T>` constraint to filter the related rows:

```C#
List<User> users = User
    .With(
        x => x.Posts,
        q => q
            .Where(x => x.Published, true)
            .Where(x => x.Views, ">", 100)
    )
    .ToList();
```

You can also order and limit a `HasMany` relation:

```C#
List<User> users = User
    .With(
        x => x.Posts,
        q => q
            .Where(x => x.Published, true)
            .OrderBy(nameof(Post.PostId), "DESC")
            .Take(5)
    )
    .ToList();
```

The strongly typed Where overloads added in 1.6.0 are also available inside eager-load constraints.

### #Nested Eager Loading

Nested relationships can be loaded from the same eager-load plan:

```C#
List<User> users = User
    .With(
        x => x.Posts,
        q => q.With(x => x.User)
    )
    .ToList();
```

Constraints can be combined with nested loading:

```C#
List<User> users = User
    .With(
        x => x.Posts,
        q => q
            .Where(x => x.Published, true)
            .With(x => x.User)
    )
    .ToList();
```

Shared nested prefixes are deduplicated in the eager-load plan.

### #Chaperone

`Chaperone` assigns the already-loaded parent instance to the inverse navigation property of each `HasMany` child when a matching `BelongsTo` relationship exists.

It can be enabled permanently on the relationship:

```C#
[HasMany(nameof(UserId), Chaperone = true)]
public List<Post> Posts { get; set; } = new();
```

or requested only for one eager load:

```C#
User user = User
    .With(
        x => x.Posts,
        q => q.Chaperone()
    )
    .First();
```

Then the inverse navigation can reuse the same parent object:

```C#
bool sameInstance = ReferenceEquals(
    user,
    user.Posts[0].User
);
```

`Chaperone()` is supported only for `HasMany` relationships.

### #Relationship Load Tracking

You can check whether a relationship has already been loaded:

```C#
User user = User
    .With(x => x.Posts)
    .First();

bool loaded = user.IsRelationLoaded(x => x.Posts);
```

A single relationship is considered loaded even when its resulting navigation value is `null`.

### #Load / LoadMissing

Load a relationship explicitly after retrieving a model:

```C#
User user = User.Find(10);
user.Load(x => x.Posts);
```

Async:

```C#
await user.LoadAsync(x => x.Posts);
```

`Load()` always refreshes the requested relationship. `LoadMissing()` only loads relationships that have not already been marked as loaded:

```C#
user.LoadMissing(x => x.Posts);
await user.LoadMissingAsync(x => x.Profile);
```

String overloads are also available.

### #Manual Relationship Queries

Use `Relation()` when you want to query a metadata relationship manually instead of eager-loading it:

```C#
User user = User.Find(10);

List<Post> posts = user
    .Relation(x => x.Posts)
    .Where(x => x.Published, true)
    .ToList();
```

`Relation()` supports both collection and single navigation properties and uses the relationship metadata to apply the parent/related key constraint automatically.

### #WhereHas

Filter parent models by the existence of related rows:

```C#
List<User> users = User
    .WhereHas(x => x.Posts)
    .ToList();
```

Add constraints with a `SubQuery<T>`:

```C#
List<User> users = User
    .WhereHas(
        x => x.Posts,
        q => q
            .Where(x => x.Published, true)
            .Where(x => x.Views, ">", 100)
    )
    .ToList();
```

Count comparisons are also supported:

```C#
List<User> users = User
    .WhereHas(x => x.Posts, ">=", 3)
    .ToList();
```

`OrWhereHas()` provides the OR equivalent.

### #WhereDoesntHave

Filter models that do not have related rows:

```C#
List<User> users = User
    .WhereDoesntHave(x => x.Posts)
    .ToList();
```

With constraints:

```C#
List<User> users = User
    .WhereDoesntHave(
        x => x.Posts,
        q => q.Where(x => x.Published, true)
    )
    .ToList();
```

`OrWhereDoesntHave()` provides the OR equivalent.

### #WithCount

`WithCount()` adds a correlated relationship count to the parent SELECT without issuing one query per model.

```C#
public int Posts_Count { get; set; }

List<User> users = User
    .WithCount(x => x.Posts)
    .ToList();
```

By default the alias is:

```text
<RelationshipName>_Count
```

You can provide a custom alias:

```C#
public int PublishedPostsCount { get; set; }

List<User> users = User
    .WithCount(
        x => x.Posts,
        q => q.Where(x => x.Published, true),
        nameof(User.PublishedPostsCount)
    )
    .ToList();
```

String overloads remain available.

### #WithExists

`WithExists()` adds a SQL `EXISTS` projection mapped as a Boolean value:

```C#
public bool Posts_Exists { get; set; }

List<User> users = User
    .WithExists(x => x.Posts)
    .ToList();
```

With a constraint and custom alias:

```C#
public bool HasPublishedPosts { get; set; }

List<User> users = User
    .WithExists(
        x => x.Posts,
        q => q.Where(x => x.Published, true),
        nameof(User.HasPublishedPosts)
    )
    .ToList();
```

The default alias is:

```text
<RelationshipName>_Exists
```

### #Relationship Aggregates

Version 1.6.0 adds `WithSum`, `WithAvg`, `WithMin` and `WithMax`.

```C#
public int? Posts_Views_Sum { get; set; }
public int? Posts_Views_Avg { get; set; }
public int? Posts_Views_Min { get; set; }
public int? Posts_Views_Max { get; set; }

List<User> users = User
    .WithSum(x => x.Posts, nameof(Post.Views))
    .WithAvg(x => x.Posts, nameof(Post.Views))
    .WithMin(x => x.Posts, nameof(Post.Views))
    .WithMax(x => x.Posts, nameof(Post.Views))
    .ToList();
```

Default aliases use:

```text
<RelationshipName>_<Column>_Sum
<RelationshipName>_<Column>_Avg
<RelationshipName>_<Column>_Min
<RelationshipName>_<Column>_Max
```

Constraints and custom aliases are supported:

```C#
public int? PublishedViewsSum { get; set; }

List<User> users = User
    .WithSum(
        x => x.Posts,
        nameof(Post.Views),
        q => q.Where(x => x.Published, true),
        nameof(User.PublishedViewsSum)
    )
    .ToList();
```

The aggregate column is validated against the related model before SQL execution.

> SQL Server aggregate semantics are preserved. `SUM`, `AVG`, `MIN` and `MAX` return `NULL` when no related row matches, so nullable result properties are recommended when the relationship may be empty.

### #Relationship Projection Notes

`WithCount`, `WithExists`, `WithSum`, `WithAvg`, `WithMin` and `WithMax` share the same relationship projection infrastructure and may be combined:

```C#
List<User> users = User
    .WithCount(x => x.Posts)
    .WithExists(x => x.Posts)
    .WithSum(x => x.Posts, nameof(Post.Views))
    .With(x => x.Posts)
    .ToList();
```

Relationship projections:

- are generated from relationship metadata;
- support string and strongly typed relationship overloads;
- support constrained `SubQuery<T>` overloads;
- validate projection aliases;
- require the parent and related model to use the same DapperGlib connection key;
- are incompatible with `Distinct()`;
- are omitted when an outer aggregate terminal such as `Count()` replaces the SELECT projection.

### #Connection Rules

Metadata-driven relationships that require related SQL execution must use the same DapperGlib connection key on both models. Cross-connection eager loading and cross-connection relationship projections are not supported.

Inside a DapperGlib transaction, relationship queries participate in the same ambient execution context when they use the same connection key.

### #Legacy Relationship<T> API

The pre-1.6 `Relationship<T>` API remains available for existing direct/manual relationship code such as relationship queries and related-model creation/deletion.

Example legacy relationship:

```C#
public Relationship<Post> PostsLegacy =>
    HasRelationship(
        new Relationship<Post>(
            localKey: "UserId",
            foreignKey: "UserId"
        )
    );
```

However, the new metadata-driven 1.6 features are based on navigation properties decorated with `[HasMany]`, `[HasOne]` or `[BelongsTo]`. A legacy `Relationship<T>` property is not used as metadata by `With`, `WithCount`, `WithExists`, relationship aggregates or the strongly typed metadata APIs.

For new code, prefer navigation properties and the 1.6 relationship metadata system.

## DB API

Version **1.4.5** introduces a Laravel-inspired `DB` API for commands that are tied to a database connection rather than to a specific `Model<T>`.

This is useful for direct Dapper queries, DTO projections, Stored Procedures, scalar values and multiple result sets without leaving DapperGlib.

### #Selecting A Connection

Use the default `SqlConnection`:

```C#
var db = DB.Connection();
```

or select a named connection from `appsettings.json`:

```C#
var db = DB.Connection("AnotherSqlConnection");
```

You can reuse the returned `DatabaseConnection` instance for multiple commands.

### #Transactions

Version **1.5.0** adds native transaction management to `DatabaseConnection`. Transactions create an ambient DapperGlib execution context so Models, Relationships, Raw queries and Stored Procedures that use the **same connection key** participate in the same SQL transaction.

#### #Automatic Transaction

Use `Transaction` when you want DapperGlib to commit automatically when the callback succeeds and roll back automatically when it throws:

```C#
DB.Connection().Transaction(() =>
{
    User.Create(new User
    {
        Name = "Keanu",
        LastName = "Reeves"
    });

    DB.Connection().Execute(
        "UPDATE Audit SET LastRun = @LastRun",
        new { LastRun = DateTime.UtcNow }
    );
});
```

For a named connection:

```C#
DB.Connection("AnotherSqlConnection").Transaction(() =>
{
    // Models and DB operations used here must also resolve to
    // the AnotherSqlConnection connection key.
});
```

The async equivalent supports `CancellationToken`:

```C#
await DB.Connection().TransactionAsync(
    async () =>
    {
        await User.CreateAsync(new User
        {
            Name = "Keanu",
            LastName = "Reeves"
        });

        await DB.Connection().ExecuteAsync(
            "UPDATE Audit SET LastRun = @LastRun",
            new { LastRun = DateTime.UtcNow }
        );
    },
    System.Data.IsolationLevel.ReadCommitted,
    cancellationToken
);
```

If the callback throws or is cancelled, DapperGlib rolls the transaction back and rethrows the original failure.

#### #Manual Transaction

Use `BeginTransaction` when your code needs to decide explicitly when to commit or roll back:

```C#
using DatabaseTransaction transaction =
    DB.Connection().BeginTransaction();

try
{
    User.Create(new User
    {
        Name = "Keanu",
        LastName = "Reeves"
    });

    transaction.Commit();
}
catch
{
    transaction.Rollback();
    throw;
}
```

If a live manual transaction is disposed without a successful commit, DapperGlib rolls it back.

Manual async transaction:

```C#
await using DatabaseTransaction transaction =
    await DB.Connection().BeginTransactionAsync(
        System.Data.IsolationLevel.ReadCommitted,
        cancellationToken
    );

try
{
    await User.CreateAsync(
        new User
        {
            Name = "Keanu",
            LastName = "Reeves"
        },
        cancellationToken
    );

    await transaction.CommitAsync();
}
catch
{
    await transaction.RollbackAsync();
    throw;
}
```

#### #Transaction Rules And Connection Isolation

- Nested DapperGlib transactions are **not supported**. Starting `Transaction`, `TransactionAsync`, `BeginTransaction` or `BeginTransactionAsync` while another DapperGlib transaction is active throws `InvalidOperationException`.
- Every operation inside the transaction must use the **same DapperGlib connection key** as the transaction. A model configured with another `Connection` value is rejected even if both keys happen to point to the same physical SQL Server database.
- A named transaction therefore requires participating models to use the same named connection key.
- Do not run multiple concurrent commands with `Task.WhenAll` on the **same transaction / connection**. Execute commands sequentially inside one transaction. If true concurrency is required, use independent connections / transactions.
- Dispose `MultipleResultReader` before issuing the next command on the same connection. This is required when MARS is disabled and is the safest pattern even when MARS is enabled.
- Independent operations and independent transactions can run concurrently; their ambient contexts are isolated.

The old `TransactionScope` pattern is no longer the primary transaction API in this documentation. Use the native DapperGlib transaction methods above when you want Model, Relationship, Raw and Stored Procedure operations to share DapperGlib's execution context.

### #Raw Query

Execute parameterized SQL and map the result to any CLR type:

```C#
List<User> users = await DB
    .Connection("SqlConnection")
    .QueryAsync<User>(
        "SELECT * FROM Users WHERE Active = @Active",
        new
        {
            Active = true
        }
    );
```

Collection expansion is handled by Dapper:

```C#
List<User> users = await DB
    .Connection("SqlConnection")
    .QueryAsync<User>(
        "SELECT * FROM Users WHERE UserId IN @Ids",
        new
        {
            Ids = new[] { 1, 2, 3 }
        }
    );
```

Sync and async versions are available:

```C#
List<User> users = db.Query<User>(sql, parameters);

List<User> usersAsync = await db.QueryAsync<User>(sql, parameters);
```

Async overloads support `CancellationToken`.

### #Raw Execute

Use `Execute` or `ExecuteAsync` for commands that do not need a result set:

```C#
int affected = await db.ExecuteAsync(
    "UPDATE Users SET Active = @Active WHERE UserId = @UserId",
    new
    {
        Active = true,
        UserId = 10
    }
);
```

### #Raw Scalar

Use `Scalar<T>` or `ScalarAsync<T>` for a single scalar value:

```C#
int total = await db.ScalarAsync<int>(
    "SELECT COUNT(*) FROM Users"
);
```

### #Raw Fluent API

You can use `Raw` when you need fluent command configuration such as a per-command timeout:

```C#
List<User> users = await db
    .Raw(
        "SELECT * FROM Users WHERE Active = @Active",
        new
        {
            Active = true
        }
    )
    .Timeout(5)
    .QueryAsync<User>();
```

The Raw builder provides:

* `Query<T>()`
* `QueryAsync<T>()`
* `Execute()`
* `ExecuteAsync()`
* `Scalar<T>()`
* `ScalarAsync<T>()`
* `QueryMultiple()`
* `QueryMultipleAsync()`
* `Timeout(seconds)`

`DB.Raw(...)` is also available as a shortcut for the default `SqlConnection`.

### #Stored Procedures

Stored Procedures are executed natively using `CommandType.StoredProcedure`.

Default connection:

```C#
var procedure = DB.Procedure(
    "dbo.usp_GetUsers"
);
```

Named connection:

```C#
var procedure = DB
    .Connection("AnotherSqlConnection")
    .Procedure(
        "dbo.usp_GetUsers"
    );
```

Add input parameters with `Parameter`:

```C#
var procedure = db
    .Procedure("dbo.usp_GetUsers")
    .Parameter("MinAge", 18)
    .Parameter("Active", true);
```

Both `Parameter("Name", value)` and `Parameter("@Name", value)` are accepted.

#### #Stored Procedure Result Sets

Map a procedure result to a model:

```C#
List<User> users = await db
    .Procedure("dbo.usp_GetUsers")
    .Parameter("MinAge", 18)
    .ToListAsync<User>();
```

or to a DTO that does not inherit from `Model<T>`:

```C#
List<UserSummaryDto> users = await db
    .Procedure("dbo.usp_UserSummary")
    .ToListAsync<UserSummaryDto>();
```

Stored Procedures support:

* `ToList<T>` / `ToListAsync<T>`
* `First<T>` / `FirstAsync<T>`
* `FirstOrDefault<T>` / `FirstOrDefaultAsync<T>`
* `Single<T>` / `SingleAsync<T>`
* `SingleOrDefault<T>` / `SingleOrDefaultAsync<T>`
* `Scalar<T>` / `ScalarAsync<T>`
* `Execute` / `ExecuteAsync`
* `QueryMultiple` / `QueryMultipleAsync`

#### #Output Parameters

Use `Output<T>` for SQL output parameters:

```C#
var procedure = db
    .Procedure("dbo.usp_ProcessUsers")
    .Parameter("MinAge", 18)
    .Output<int>("Total")
    .Output<string>("Message", size: 200);

await procedure.ExecuteAsync();

int total = procedure.Get<int>("Total");
string message = procedure.Get<string>("Message");
```

For string output parameters, define the appropriate `size`.

#### #InputOutput Parameters

```C#
var procedure = db
    .Procedure("dbo.usp_ProcessUsers")
    .InputOutput("Accumulator", 10);

await procedure.ExecuteAsync();

int accumulator = procedure.Get<int>("Accumulator");
```

#### #Return Values

SQL Server procedure return values are supported:

```C#
var procedure = db
    .Procedure("dbo.usp_ProcessUsers")
    .ReturnValue();

await procedure.ExecuteAsync();

int returnValue = procedure.Get<int>("ReturnValue");
```

Output and return values can only be read after the procedure has completed.

#### #Stored Procedure Timeout And Cancellation

```C#
var result = await db
    .Procedure("dbo.usp_LongProcess")
    .Timeout(10)
    .ScalarAsync<int>(cancellationToken);
```

Per-procedure timeout overrides the global `DapperGlib:CommandTimeout`.

### #QueryMultiple

Version **1.4.5** adds support for multiple result sets through `MultipleResultReader`.

Stored Procedure example:

```C#
using MultipleResultReader result = await db
    .Procedure("dbo.usp_Dashboard")
    .QueryMultipleAsync();

List<User> users = await result.ReadAsync<User>();
List<Comment> comments = await result.ReadAsync<Comment>();
DashboardSummary summary =
    await result.ReadSingleAsync<DashboardSummary>();
```

Raw SQL can also return multiple result sets:

```C#
using MultipleResultReader result = await db
    .QueryMultipleAsync(
        @"
        SELECT TOP (10) * FROM Users;
        SELECT TOP (10) * FROM Comments;
        "
    );

List<User> users = await result.ReadAsync<User>();
List<Comment> comments = await result.ReadAsync<Comment>();
```

`MultipleResultReader` supports:

* `Read<T>` / `ReadAsync<T>`
* `ReadFirst<T>` / `ReadFirstAsync<T>`
* `ReadFirstOrDefault<T>` / `ReadFirstOrDefaultAsync<T>`
* `ReadSingle<T>` / `ReadSingleAsync<T>`
* `ReadSingleOrDefault<T>` / `ReadSingleOrDefaultAsync<T>`

Always dispose the reader, preferably with `using`, so the underlying DataReader and database connection are closed correctly.

When using Stored Procedure `Output` or `ReturnValue` parameters together with `QueryMultiple`, read those values **after** the `MultipleResultReader` has been disposed:

```C#
var procedure = db
    .Procedure("dbo.usp_Dashboard")
    .Output<int>("Total")
    .ReturnValue();

using (MultipleResultReader result =
    await procedure.QueryMultipleAsync())
{
    List<User> users =
        await result.ReadAsync<User>();
}

int total = procedure.Get<int>("Total");
int returnValue =
    procedure.Get<int>("ReturnValue");
```


## Version 1.6.0 Highlights

Version **1.6.0** focuses on relationships, eager loading and safer fluent query composition while keeping the Dapper-based execution model.

- Added metadata-based `[HasMany]`, `[HasOne]` and `[BelongsTo]` navigation properties.
- Added `With()` eager loading for `HasMany`, `HasOne` and `BelongsTo`.
- Added multiple and nested eager loading with shared-path deduplication.
- Added eager-load constraints through `EagerLoadBuilder<T>`.
- Added grouped secondary-query eager loading to avoid automatic `HasMany` JOIN row multiplication.
- Added SQL Server parameter-budget chunking for eager relationship queries.
- Added per-parent `Skip` / `Take` for `HasMany` using `ROW_NUMBER() OVER (PARTITION BY ...)`.
- Added relationship load tracking with `IsRelationLoaded()`.
- Added `Load`, `LoadAsync`, `LoadMissing` and `LoadMissingAsync`.
- Added `Chaperone` for reusing the loaded parent instance on inverse `BelongsTo` navigation properties.
- Added metadata-driven `Relation()` for manual relationship queries.
- Added strongly typed lambda overloads for `WhereHas`, `OrWhereHas`, `WhereDoesntHave` and `OrWhereDoesntHave`.
- Reworked `WithCount()` to use relationship metadata instead of parsing legacy relationship SQL.
- Added `WithExists()`.
- Added `WithSum`, `WithAvg`, `WithMin` and `WithMax` relationship projections.
- Added shared relationship projection handling with alias validation, parameterized constraints and connection-key isolation.
- Added strongly typed lambda overloads for the Where family on `Model<T>`, `QueryBuilder<T>`, `SubQuery<T>` and `EagerLoadBuilder<T>`.
- Preserved string-based query overloads for compatibility.
- Preserved parameterized SQL generation and `ToSql()` / `ToParameterizedSql()` inspection support.
- Evaluated Dapper Multi-Mapping for automatic eager loading; grouped secondary queries remain the default relationship loading strategy.

### #Migration From 1.5.x To 1.6.0

Version 1.6.0 keeps the existing Query Builder and DB APIs, but introduces a new relationship model for eager loading and metadata-driven relationship features.

#### Legacy relationship definition

Before 1.6, relationship properties were commonly defined as query objects:

```C#
public Relationship<Post> Posts =>
    HasRelationship(
        new Relationship<Post>(
            localKey: "UserId",
            foreignKey: "UserId"
        )
    );
```

#### 1.6 navigation relationship

For the new eager-loading and metadata APIs, use a navigation property:

```C#
[HasMany(nameof(UserId))]
public List<Post> Posts { get; set; } = new();
```

and define the inverse relationship when required:

```C#
[BelongsTo(nameof(UserId))]
public User? User { get; set; }
```

If the key names are different, specify both:

```C#
[HasMany(nameof(UserId), nameof(Post.AuthorId))]
public List<Post> Posts { get; set; } = new();
```

#### Manual queries

Legacy code may continue using the legacy relationship property. New metadata relationships can be queried manually through `Relation()`:

```C#
List<Post> posts = user
    .Relation(x => x.Posts)
    .Where(x => x.Published, true)
    .ToList();
```

#### Eager loading

New in 1.6:

```C#
List<User> users = User
    .With(x => x.Posts)
    .ToList();
```

#### Where clauses

String overloads remain valid:

```C#
User.Where("UserId", 10).First();
```

You can migrate incrementally to strongly typed overloads:

```C#
User.Where(x => x.UserId, 10).First();
```

#### WithCount migration

`WithCount()` in 1.6 resolves relationship metadata. A legacy `Relationship<T>` property is no longer the relationship source for this API.

Use:

```C#
public int Posts_Count { get; set; }

[HasMany(nameof(UserId))]
public List<Post> Posts { get; set; } = new();

var users = User.WithCount(x => x.Posts).ToList();
```

### #1.6 Compatibility Notes

- Existing string-based Where APIs remain available.
- Existing DB, Raw SQL, Stored Procedure and transaction APIs remain available.
- The legacy `Relationship<T>` API remains available for compatible manual relationship operations.
- Metadata-based eager loading and relationship projections require `[HasMany]`, `[HasOne]` or `[BelongsTo]` navigation properties.
- `With()` does not switch queries to automatic JOINs; related data is loaded with grouped secondary queries.
- `Distinct()` cannot be combined with relationship projections such as `WithCount`, `WithExists` or relationship aggregates.
- Parent and related models must use the same DapperGlib connection key for eager loading and relationship projections.
- Lazy loading is not enabled automatically.
- Internal relationship metadata, eager-load planning, chunking and projection infrastructure are implementation details and are not part of the public API contract.

### #Choosing A Multi-Insert API

Use `CreateMany` when you need generated primary keys back in the model instances. Use `InsertMany` when you want efficient parameterized batching but do not need generated identities in memory. Use `BulkInsert` for the highest-throughput SQL Server path when identity hydration is not required.

## Still is Dapper
DapperGlib continues to be built on top of Dapper. Version 1.6.0 expands the higher-level APIs with metadata relationships, eager loading and strongly typed query overloads while preserving the batching and transaction capabilities introduced in 1.5.0. You can still access the underlying Dapper interface by instantiating the context whenever you need direct control.

```C#
using Dapper;
using DapperGlib;

GlipContext _context = new();

using var conection = _context.CreateConnection();
var users = conection.Query<User>("SELECT * FROM Users");

```
